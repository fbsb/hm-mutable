# hm-mutable

Manage writable files and directories with Home Manager. Selected entries are
copied instead of symlinked to the Nix store, so applications can modify them
at runtime. Every activation restores their declaratively configured contents.

## Use

Add this flake as an input to your configuration:

```nix
inputs.hm-mutable.url = "github:fbsb/hm-mutable";
```

Import `homeManagerModules.default` in your Home Manager configuration:

```nix
home-manager.lib.homeManagerConfiguration {
  inherit pkgs;
  modules = [
    hm-mutable.homeManagerModules.default
    ./home.nix
  ];
}
```

For NixOS or nix-darwin, add it to `home-manager.sharedModules` instead:

```nix
home-manager.sharedModules = [ hm-mutable.homeManagerModules.default ];
```

Enable writable copies globally, or select individual entries with `mutable = true`:

```nix
{
  home.mutableFiles = true;
  home.mutableFilesCopyCommand = "cp"; # Or "rsync".

  xdg.configFile."example/settings.json".text = ''{"theme":"light"}'';

  home.file.".immutable" = {
    text = "Keep this linked to the Nix store.";
    mutable = false;
  };
}
```

`home.mutableFiles` defaults to `false`. Each entry's nullable `mutable` option
inherits that default; `true` opts in and `false` opts out. Supported entry sets
are `home.file` and `xdg.configFile`, `dataFile`, `cacheFile`, and `stateFile`.
This includes entries generated by other Home Manager modules.

### With Den

With [Den](https://den.denful.dev/), add the `hm-mutable` flake input as above,
then define an aspect in a module loaded by your Den configuration:

```nix
{ inputs, config, ... }:
{
  den.aspects.mutable-files.homeManager = {
    imports = [ inputs.hm-mutable.homeManagerModules.default ];
    home.mutableFiles = true;
  };

  den.aspects.alice.includes = [ config.den.aspects.mutable-files ];
}
```

Replace `alice` with your existing user or standalone home aspect. Include
`mutable-files` in each aspect that should use it; defining it alone does not
activate it. To select individual files instead, omit `home.mutableFiles = true`
and set `mutable = true` on those entries in their `homeManager` configuration.

The `inputs` argument is captured by the enclosing configuration module, so
the Home Manager module does not need extra special arguments or Den's
`flake-scope` battery. See Den's
[class module documentation](https://den.denful.dev/explanation/class-modules/#flake-inputs-and-specialargs)
for details about importing modules from flake inputs.

## Behavior And Safety

- Mutable files and directory trees are copied, made user-writable, and replaced
  on **every activation**. Existing destination contents and runtime edits are
  deleted, regardless of `force`. Do not use this for data you want to preserve.
- A directory is copied as a whole, whether or not `recursive` is set. Source
  symlinks are dereferenced so nested files are writable copies too; sources
  must not contain dangling or cyclic symlinks. Executable bits are inherited
  unless a file's `executable` option explicitly changes them.
- Mutable `onChange` hooks run on every non-dry-run activation, after all copies
  are installed and before Home Manager's immutable `onChange` hooks. Immutable
  entries retain normal linking and change detection.
- Removed or disabled mutable entries are deleted on the next activation,
  including any runtime data created inside a managed directory.
- Changing a linked entry to mutable works automatically. For mutable-to-linked
  transitions, set `force = true` on the new immutable entry, or arrange an
  Home Manager backup. Home Manager's pre-write collision check can otherwise reject
  the old edited copy before this module's cleanup runs. This also applies
  when turning off the global default.
- Mutable targets must be non-overlapping, normalized paths inside the home
  directory. Tabs, newlines, and the `.metadata` manifest root are reserved.
  An existing symlink in a destination's parent path is rejected instead of
  writing through it.
- Keep this module imported for one activation after
  removing your last mutable entry; removing the module itself disables cleanup.
- As with normal Home Manager sources, source contents live in the Nix store.
  This is not a mechanism for managing secrets.

## Implementation

The module extends the existing file submodule types with `mutable`. An
`apply` on `home.file` retains mutable entries for this module but disables
them for Home Manager's linker and change hooks. It does not change `enable` on
the XDG entry sets themselves, so XDG forwarding still works.

Activation DAG entries clean up the old manifest after `writeBoundary`, let
Home Manager process immutable links, then copy mutable entries and run their
hooks before `onFilesChange`. `home.extraBuilderCommands` attaches the manifest
to the generation so removed entries can be cleaned up on the next activation.

## Tests

From this repository:

```sh
nix flake check path:. --print-build-logs
```

Checks run against pinned Home Manager master and release 26.05, each with its own
Nixpkgs input. For each version, both `cp` and `rsync` tests build real Home
Manager generations and execute the actual file-related activation DAG nodes
in a sandbox with a private `$HOME`. They do not switch your Home Manager
profile or install anything in your real home.

Coverage includes global defaults, explicit opt-outs, disabled entries, all four
XDG sets, quoted paths, directory copies, dereferenced source symlinks, executable
permissions, repeated resets, hook timing, dry runs, removal, both link/copy
transitions, generation manifest cleanup, and symlink-parent rejection.
Additional evaluation checks reject escaping paths and overlapping targets.

To test newer Home Manager and Nixpkgs revisions:

```sh
nix flake update --flake path:.
nix flake check path:. --print-build-logs
```

The GitHub Actions workflow runs on pushes, pull requests, manual dispatch, and
a weekly schedule. Its Linux and macOS jobs test both the lock file and freshly
updated inputs. Updated-input failures expose upstream compatibility regressions;
the workflow does not commit dependency updates. No test can guarantee
compatibility with future versions that have not been released yet.
